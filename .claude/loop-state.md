# Implementation plan: flaky-test detection excluded from circuit-breaker and failure counts (issue #8326)

## Summary

Today every non-zero test exit counts as a regression. A single flaky test can therefore steer the agent into chasing a bug that isn't there, push it toward the circuit breaker, and make the daemon classify the run as `build_failure`. Pausing and retrying then follow from that classification. This plan adds `scripts/lib/test-flakiness.sh`. When exactly one test fails, it reruns that test once on its own and labels the failure `flaky` or `regression`. The loop, `error-summary.json`, the daemon classifier and `daemon metrics` then act on that label.

### What the codebase does today (this changes the design)

- **What the circuit breaker counts.** `CONSECUTIVE_FAILURES` (`scripts/sw-loop.sh:2508`) counts *low-progress iterations*, measured by `check_progress` in `scripts/lib/loop-convergence.sh:46`. It does not count test failures directly. A flaky failure feeds it indirectly: the agent is told "TESTS FAILED — fix these" (`loop-iteration.sh` `compose_prompt`), spends the iteration on a non-bug, makes a small diff, and the iteration counts as stagnant. The fix therefore goes in two places:
  1. the test gate, so the agent isn't told to fix a flaky test;
  2. the increment site, so a flaky-only iteration doesn't count.
- **What `write_error_summary` does.** It lives at `scripts/sw-loop.sh:1105` and **deletes** `error-summary.json` whenever tests pass. If a flaky rerun turns the gate green, that path has to change, or the flaky record is lost.
- **How the daemon classifies.** `classify_failure` (`scripts/lib/daemon-failure.sh:22`) greps the issue log for `FAIL` and returns `build_failure`. It already reads `.claude/loop-logs/progress.md` from the worktree, so reading `error-summary.json` from the same directory is an established pattern.
- **What `daemon metrics --json` reports.** It is built in `scripts/sw-daemon.sh:1270`. It has no failure-class breakdown, although `daemon.failure_classified` events are already emitted.

## Testing Strategy Expertise

Apply these testing patterns:

### Test Pyramid
- **Unit tests** (70%): Test individual functions/methods in isolation
- **Integration tests** (20%): Test component interactions and boundaries
- **E2E tests** (10%): Test critical user flows end-to-end

### What to Test
- Happy path: the expected successful flow
- Error cases: what happens when things go wrong?
- Edge cases: empty inputs, maximum values, concurrent access
- Boundary conditions: off-by-one, empty collections, null/undefined

### Test Quality
- Each test should verify ONE behavior
- Test names should describe the expected behavior, not the implementation
- Tests should be independent — no shared mutable state between tests
- Tests should be deterministic — same result every run

### Coverage Strategy
- Aim for meaningful coverage, not 100% line coverage
- Focus coverage on business logic and error handling
- Don't test framework code or simple getters/setters
- Cover the branches, not just the lines

### Mocking Guidelines
- Mock external dependencies (APIs, databases, file system)
- Don't mock the code under test
- Use realistic test data — edge cases reveal bugs
- Verify mock interactions when the side effect IS the behavior

### Regression Testing
- Write a failing test FIRST that reproduces the bug
- Then fix the bug and verify the test passes
- Keep regression tests — they prevent the bug from recurring
