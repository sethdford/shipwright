# Plan: cost-per-successful-pipeline trend and budget headroom in the dashboard (#7099)

## What the code looks like today

- **The obvious data source is empty.** `scripts/sw-cost.sh:339` defines `cost_record_outcome()`, which writes `~/.shipwright/cost-outcomes.json`. Nothing in `scripts/` calls it, so that file is normally missing or empty. The reliable source is the `pipeline.completed` event. `scripts/lib/pipeline-commands.sh:986` and `:1058` emit it with `result=success|failure`, `total_cost`, `issue` and `template`. `emit_event` writes numeric values as JSON numbers.
- **Old events get cut off.** `readEvents()` (`dashboard/server.ts:948`) returns only the latest 200 rows from SQLite, or the last 1000 JSONL lines. On a busy system, loop and stage events push `pipeline.completed` events out of that window long before 14 days have passed. The existing `/api/costs/trend` has the same problem.
- **Budget data already exists.** `getCostInfo()` (`server.ts:2039`) returns `{today_spent, daily_budget, pct_used}` from the DB or from `costs.json`/`budget.json`. It can be reused as is.
- **There is an existing bug next to this work.** `/api/costs/trend` returns `{daily:[...]}`, but `fetchCostTrend` and `renderCostTrend` (`dashboard/src/views/metrics.ts:236`) read `data.points`. The current cost-trend card therefore always shows "No trend data". I'm noting it here but leaving it out of scope (see Notes).
- **Test mock needs a fix.** The `budget.json` mock in `sw-server-api-test.sh` uses `daily_limit`, but the server reads `daily_budget_usd`. As written, the mock produces an "unlimited" budget.

## Brainstorming and alternatives

**Minimum change that meets the issue:** one GET endpoint, one widget in the existing Metrics view, and tests at the server-API and vitest levels.

| Approach | Pros | Cons | Verdict |
|---|---|---|---|
| **A. Aggregate `pipeline.completed` events on the server, with a type-filtered event reader** | Uses data that is actually recorded; no bash changes; not limited by the 200-event cap | Needs a new reader helper | **Chosen** |
| B. Read only `cost-outcomes.json` | Matches `sw-cost.sh` semantics | Nothing writes the file, so the widget would always be empty. Wiring `cost_record_outcome` into the pipeline touches a hot path. | Used only as a fallback |
| C. Shell out to `sw-cost.sh efficiency --json` | One source of truth | Spawns a process per request, depends on jq/bash, has no daily breakdown, adds latency | Rejected |
| D. Push the data over WebSocket in `FleetState` | Real time | Cost trends change slowly; it makes every broadcast bigger | Rejected; poll when the view renders |
