## Key findings

1. **There is one writer of `error-summary.json`** (`write_error_summary`, `scripts/sw-loop.sh:1105`). Its shape is `{iteration, timestamp, error_count, error_lines[], test_cmd}`. It has one prompt consumer, `scripts/lib/loop-iteration.sh:106-118`, which reads `.error_count` and `.error_lines[]` (at most 10 lines). There are also two restart consumers in `scripts/lib/session-restart.sh:54,395`. New fields can be added without breaking any of them.
2. **The insertion point is `run_single_agent_loop`** (`scripts/sw-loop.sh:2137`), after init/resume and `show_banner`, before `while true`. `ITERATION` is still 0 there.
3. **This is the most important hazard.** `run_loop_with_restarts` (`scripts/sw-loop.sh:2575-2690`) restarts on any status other than `complete`, up to `MAX_RESTARTS` (3 for daemon runs). A hard environment failure would trigger up to 3 restarts, each re-running validation and producing nothing. The pipeline's failure handler (`scripts/lib/pipeline-stages-build.sh:458-476`) would also tag it as `context_exhaustion`, and the daemon then *raises* `--max-restarts` on retry. This must be short-circuited (see Failure Mode FM-1).
4. **`preflight_checks()` already exists** (`scripts/lib/pipeline-util.sh:255`). It checks tools, git state and GitHub auth for the *pipeline*. It does not look at the target project's dependencies, syntax or test runner, so the two don't overlap. The new check belongs in the **loop**, so it also protects plain `shipwright loop` runs, not only pipelines.
5. **`_timeout` falls back to running with no timeout** when neither `timeout` nor `gtimeout` exists (stock macOS, `scripts/lib/compat.sh:252`). A "smoke" run of the test command could then quietly become a full 15-minute test run.
6. **Tests:** `sw-test-all.sh` auto-discovers `scripts/*-test.sh`, so a new suite needs no `package.json` change. `sw-loop-test.sh` pulls functions out of `sw-loop.sh` with `sed`, which is fragile. Putting the logic in a **new lib file** lets tests `source` it directly.

## Build Environment Validation Pattern

Pre-build validation catches environment failures (broken dependencies, syntax errors, test-runner startup) before wasting a full loop iteration. The pattern integrates tightly with the build loop's error-feedback system.

### Core Contract

**Inputs:**
- Changed files (from git diff)
- Project type detection (package.json, Cargo.toml, etc.)
- Config flag `loop.pre_build_validate_enabled` (default: true)

**Outputs on failure:**
- `error-summary.json` matching the shape the loop already reads
- Each error entry: `{"line": "...", "message": "..."}`
- Exit code 1 (non-fatal; loop treats it as a failed pre-flight, not a fatal error)

**Outputs on success:**
- Clean exit code 0
- Optional validation log file for observability

### Check Categories

1. **Dependency Install** — Run package manager (npm ci, cargo fetch, pip install --dry-run) with a short timeout (10s). Catches missing deps, lockfile corruption, network issues.

2. **Syntax Check** — Lint only changed files using the project's existing linter (eslint, cargo check, mypy) if available. Skip if no linter configured. Report first 5 errors to avoid overwhelming context.

3. **Test Runner Startup** — Run test command with `--help` or `--list` (or equivalent) to verify the test runner even starts. Catches test config errors without running actual tests.

### Integration Points

- **Error Feedback**: When validation fails, `sw-loop.sh` reads `error-summary.json` and injects it as structured context into the next iteration. Pre-flight failures surface the same way as loop errors.

- **Conditional Execution**: Check `daemon-config.json` for `loop.pre_build_validate_enabled`. Respect the flag; allow skipping for environments where pre-flight is not applicable.

- **No Retry**: Pre-flight failures don't auto-retry the validation itself. The loop's normal retry logic handles re-attempts on the full build.

### Failure Handling

Pre-flight failures are logged but not fatal—the loop enters with the validation error as structured context, giving the agent a chance to fix and retry. If pre-flight fails 3 times in a row, the loop's circuit-breaker trips as normal (treating it like any other error).

## Observability: Watch the Deploy Like a Hawk

Post-deploy monitoring catches what tests miss. Real traffic reveals real problems.

### What to Monitor (by Priority)

**P0 — Immediate (first 5 minutes):**
- Error rate: any increase over baseline?
- Health check: still returning 200?
- Latency: p50/p95/p99 within normal range?
- Memory/CPU: any sudden spikes?

**P1 — Short-term (5-30 minutes):**
- Business metrics: are users completing key flows?
- Queue depths: are background jobs processing normally?
- Connection pools: any exhaustion or leak patterns?
- Disk usage: any unexpected growth?

**P2 — Medium-term (1-24 hours):**
- Memory trends: gradual leak over time?
- Error rate trends: slowly increasing?
- User-reported issues: any new support tickets?
- Performance degradation under sustained load?

### Anomaly Detection Patterns
- **Spike detection**: >2x baseline error rate in any 1-minute window
- **Trend detection**: steadily increasing error rate over 5-minute window
- **Absence detection**: expected periodic events stop occurring
- **Latency shift**: p95 latency increases >50% from baseline

### Log Analysis
- Search for new ERROR/FATAL/PANIC entries not present before deploy
- Check for stack traces — they indicate unhandled exceptions
- Look for retry storms — repeated failed attempts at the same operation
- Monitor for resource exhaustion messages (OOM, connection refused, disk full)

### Auto-Rollback Triggers
Automatically rollback if ANY of these occur:
- Health check fails 3 consecutive times
- Error rate exceeds threshold for 2+ minutes
- Critical service dependency becomes unreachable
- Memory usage exceeds 90% of limit

### Monitoring by Issue Type

**Frontend changes:**
- JavaScript error rates in browser (if client-side monitoring exists)
- Asset load failures (404s on new bundles)
- Core Web Vitals regression (LCP, FID, CLS)

**API changes:**
- Response status code distribution (2xx vs 4xx vs 5xx)
- Request throughput — drops indicate client-side breakage
- Authentication failures — spikes indicate auth regression

**Database changes:**
- Query latency per endpoint
- Connection pool utilization
- Slow query log entries
- Replication lag (if applicable)

### Incident Escalation
If monitoring detects issues:
1. Execute rollback (if auto-rollback enabled)
2. Create incident issue with monitoring data
3. Attach relevant logs and metrics
4. Tag the original issue with `incident` label
5. Do NOT silence alerts — let them fire
