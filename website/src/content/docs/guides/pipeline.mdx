The delivery pipeline (`shipwright pipeline`) automates the entire software development lifecycle. Start from a GitHub issue or a goal description and Shipwright handles planning, building, testing, reviewing, and PR creation.

## Pipeline Stages

```
intake → spec_generation → plan → design → build → test → review → spec_verification → compound_quality → audit → pr → merge → deploy → validate → monitor
```

15 stages. Each template enables a subset of them, and each enabled stage has a gate: `auto` proceeds immediately, `approve` pauses for approval.

| Stage                 | What Happens                                                                 |
| --------------------- | ---------------------------------------------------------------------------- |
| **intake**            | Fetch issue metadata from GitHub, or parse the goal description              |
| **spec_generation**   | Turn the issue or goal into acceptance criteria and edge cases               |
| **plan**              | Claude generates an implementation plan with tasks and approach              |
| **design**            | Design interfaces, data models, and API contracts                            |
| **build**             | Delegates to `shipwright loop` for autonomous multi-iteration development    |
| **test**              | Run the test suite and validate coverage                                     |
| **review**            | Claude reviews the changes for quality, security, and correctness            |
| **spec_verification** | Check the implementation against the acceptance criteria                     |
| **compound_quality**  | Multi-dimensional quality audit — adversarial, negative, e2e, DoD            |
| **audit**             | Additional checks such as secret scanning, file permissions, and coverage delta |
| **pr**                | Create a GitHub PR with labels, milestone, and reviewers                     |
| **merge**             | Squash-merge the PR, with an optional CI wait                                |
| **deploy**            | Deploy to staging or production (if configured)                              |
| **validate**          | Post-deploy smoke tests and health URL checks                                |
| **monitor**           | Watch for errors post-deploy, with auto-rollback where configured            |

## Pipeline Templates

Pass a template with `--pipeline <name>` (default: `standard`). There are nine templates:

| Template     | Enabled stages | Approval gates                                   | Use Case                   |
| ------------ | -------------- | ------------------------------------------------ | -------------------------- |
| `fast`       | 6              | none (all auto)                                  | Quick fixes                |
| `hotfix`     | 6              | none (all auto)                                  | Urgent production fixes    |
| `standard`   | 11             | plan, design, review, pr, merge                  | Normal feature work        |
| `tdd`        | 11             | plan, design, review, pr, merge                  | Test-first feature work    |
| `full`       | 15             | plan, design, review, pr, merge, deploy          | Production deployment      |
| `autonomous` | 13             | none (all auto; deploy and validate disabled)    | Fully autonomous operation |
| `deployed`   | 14             | deploy                                           | Deploy plus monitoring     |
| `enterprise` | 14             | all except spec_generation and spec_verification | Maximum safety             |
| `cost-aware` | 10             | plan, review, pr (deploy and validate disabled)  | Budget-limited delivery    |

See the [Templates reference](/shipwright/reference/templates/) for the full stage list and key config of each template.

Browse templates:

```bash
shipwright pipeline list        # List all templates
shipwright pipeline show standard  # View template details
```

## Intelligence-Composed Pipelines

When the intelligence layer is enabled, Shipwright can compose custom pipelines dynamically instead of using static templates. The intelligence engine analyzes the issue semantically and builds a tailored stage configuration — adding extra stages for high-risk changes, removing unnecessary stages for simple fixes, and routing each stage to the optimal model (opus, sonnet, or haiku) based on task complexity and remaining budget.

Static templates remain as fallbacks when intelligence is disabled or when a Claude API call fails. See the [Intelligence guide](/shipwright/guides/intelligence/) for configuration details.

## Self-Healing Builds

When tests fail after a build, the pipeline automatically captures the error output and re-enters the build loop with that context — just like a human developer reading test failures and fixing them.

```bash
# Allow up to 3 self-healing cycles
shipwright pipeline start --goal "Build payment flow" --self-heal 3
```

The compound quality stage orchestrates this: it runs tests, and if they fail, feeds the failure output back to the build agent as context for the next iteration.

## GitHub Integration

The pipeline integrates with GitHub when starting from an issue:

- **Auto-fetches** issue title, body, labels, and milestone
- **Self-assigns** the issue to signal work has started
- **Posts progress comments** as stages complete
- **Creates PRs** with labels, milestone, and reviewers propagated from the issue
- **Closes the issue** in the monitor stage, but only when `close_issue` is `true` in the validate stage config (`validate.config.close_issue`) and the monitor stage runs

## Auto-Detection

Shipwright automatically detects your project configuration:

- **Test command** — detected for common project types such as npm, pytest, go test, and cargo test
- **Branch prefix** — derived from task type (feature/, fix/, hotfix/)
- **Reviewers** — from CODEOWNERS or git history
- **Language and framework** — for context-aware planning

## Managing Pipelines

```bash
# Resume a pipeline from where it left off
shipwright pipeline resume

# Check pipeline progress
shipwright pipeline status

# Abort a running pipeline
shipwright pipeline abort
```

## Notifications

Get notified about pipeline events via webhooks:

```bash
# Slack webhook
shipwright pipeline start --goal "Add auth" --slack-webhook https://hooks.slack.com/...

# Custom webhook (via environment variable)
export SHIPWRIGHT_WEBHOOK_URL=https://your-webhook.example.com
shipwright pipeline start --goal "Add auth"
```

## Pipeline State

Pipeline progress is tracked in `.claude/pipeline-state.md` and artifacts are stored in `.claude/pipeline-artifacts/`. This allows pipelines to be resumed after interruption.
