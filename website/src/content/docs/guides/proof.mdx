A software factory has to show its outcomes, not describe its features. The proof engine is three
commands that measure Shipwright from the outside:

| Command | Question it answers |
| --- | --- |
| `shipwright scorecard` | How do the factory's own PRs actually fare: merged, merged without help, reverted, how fast, at what cost? |
| `shipwright eval` | Is a candidate policy (a new default, a lesson, a routing table) really better than the incumbent on the same cases? |
| `shipwright bench` | Does Shipwright resolve more tasks than bare Claude Code with the same model, graded by tests neither saw? |

The rules behind them come from [ADR-0009](https://github.com/sethdford/shipwright/blob/main/docs/adr/0009-closed-loop-learning.md):
every adaptive decision is logged, the evaluator is outside the agent's reach, and a policy change
ships only through a paired ratchet.

## Delivery scorecard

```bash
shipwright scorecard                      # last 30 days, text
shipwright scorecard --days 90 --format markdown > scorecard.md
shipwright scorecard --exclude 195,6765   # leave known test-run PRs out
```

It reports, for the factory's own PRs in the current repository:

| Measure | Definition |
| --- | --- |
| **Merge rate** | Merged agent PRs ÷ closed agent PRs in the window |
| **Merged without human help** | Merged agent PRs with no commit, before or after the PR opened, by anyone other than `shipwright[bot]`, `github-actions[bot]` or `claude[bot]` |
| **Revert rate** | Merged agent PRs reverted by a merged `Revert "…"` PR within 14 days. Merges still inside the 14-day window are counted separately |
| **Median time to merge** | From PR opened to merged |
| **Cost per merged PR** | Spend from `~/.shipwright/costs.json` joined to merged PRs. Shown as `unknown`, never $0, when the ledger holds no real cost for the window |

**What counts as an agent PR:** its body carries "Generated by `shipwright pipeline`", or its
branch starts with `ci/issue-`. **Test runs** (label `shipwright:test-run`, a `test/` branch, or a
number passed with `--exclude`) are left out of every metric and reported as an excluded count.

The command is read-only. It lists closed PRs through `gh` over REST, filters by close date
locally, and reads commits only for merged agent PRs. `--format markdown` is meant for a public
scorecard page.

<Aside type="note" title="The first baseline">
Measured over the REST API on 2026-11-26, before this stack shipped: of 10 pipeline-authored PRs
in this repository since February 2026, 2 merged. That is the number the rest of this page exists
to move, and to prove moved.
</Aside>

## Eval ratchet

```bash
shipwright eval score   --results candidate.json --k 3
shipwright eval ratchet --incumbent incumbent.json --candidate candidate.json --k 3 --json
```

A results file holds the runs of one policy over a set of eval cases:

```json
{
  "policy": "routing-v1",
  "runs": [
    { "case": "c01", "pass": true, "costUsd": 0.42 },
    { "case": "c01", "pass": true, "costUsd": 0.39 }
  ],
  "vetoes": { "fenceViolations": 0, "protectedPathTouched": false, "oracleTampering": false }
}
```

- **pass^k** is the chance that k runs of the same case all pass, estimated without bias as
  C(passes, k) ÷ C(runs, k). Every case needs at least k runs (default 3).
- **ratchet** accepts the candidate only when it is **non-inferior** (losses minus wins ≤ 0, and at
  most one loss) **and** either **superior** (exact one-sided sign test, p ≤ 0.05) or **cheaper**
  (median paired cost ratio ≤ 0.9).
- A fence violation, a touch of a protected path, or oracle tampering **vetoes** the candidate
  outright.

Exit 0 means scored or accepted, 3 means rejected. Both commands are pure: they read the files and
write nothing.

### What the ratchet decides

Every new default in this release has an off switch so it can be measured this way
([full list](https://github.com/sethdford/shipwright/blob/main/docs/reference/switches.md)):

| Feature | Control arm |
| --- | --- |
| Acceptance tests (on by default) | `SW_ACCEPTANCE=off` |
| Governance brief | `SHIPWRIGHT_GOVERNANCE=off` |
| Repository lessons | `SHIPWRIGHT_LESSONS=off` |
| A proposed lesson | `SHIPWRIGHT_LESSONS_TRIAL=L-NNNN` as the candidate |
| Repository world model | `SHIPWRIGHT_REPO_MODEL=off` |
| Compute router | `SHIPWRIGHT_ROUTER=shadow` vs `apply` |
| Tournament mode | `PIPELINE_ATTEMPTS=1` vs `3` |

## Head-to-head benchmark

`shipwright bench` runs each **arm** on the same tasks, from the same base commit, with the same
model, permission policy and time limit, and grades every run with hidden tests. Design:
[ADR-0013](https://github.com/sethdford/shipwright/blob/main/docs/adr/0013-head-to-head-benchmark.md).

| Arm kind | Runs |
| --- | --- |
| `claude-code` | `claude -p --output-format json --settings config/agent-permissions.json` |
| `shipwright` | `shipwright pipeline start --local --headless`, with `attempts` mapped to `PIPELINE_ATTEMPTS` |
| `command` | any agent CLI, from an argv template with `{model}` and `{problem_file}` |

No arm gets a GitHub token. Arms can carry `SHIPWRIGHT_*` and `PIPELINE_*` variables, so the same
benchmark measures ablations and lesson trials.

  <TabItem label="Holdout suite">

```bash
# Tasks mined from merged PRs that close an issue; keep only fair ones
shipwright bench mine-holdout --repo OWNER/NAME --since 2026-10-01 \
  --setup "bun install --frozen-lockfile" > ~/bench/holdout.json
shipwright bench validate --tasks ~/bench/holdout.json --out ~/bench/validate

# Run count and estimated spend; nothing runs
shipwright bench plan --tasks ~/bench/holdout.json --arms arms.json --trials 3

# Run under a hard budget (resumable), then report
shipwright bench run --tasks ~/bench/holdout.json --arms arms.json \
  --out ~/bench/results --trials 3 --budget 150
shipwright bench report --tasks ~/bench/holdout.json --arms arms.json --out ~/bench/results --k 3
```

**How a holdout task is built.** The issue is the problem statement, the merge commit's parent is
the base, the PR's test changes are the hidden oracle, and the merge commit is the gold fix.
`validate` keeps only tasks whose oracle fails on the base and passes on the gold fix. When a run
is graded, files the oracle touches are reset to the base before it is applied, so an agent that
edits the tests cannot pass.

**The report** (`report.md`, `report.html`, `report.json`) shows the resolve rate with a 95% Wilson
interval, pass^k, spend, dollars per resolved task (only when every run reported spend), median
minutes, and an exact two-sided sign test of each arm against the baseline. `export-eval --arm ID`
writes an arm in the eval results format, so a benchmark run feeds `eval ratchet` directly.

**Cost control.** `run` requires `--budget` and stops before any run the budget cannot cover,
counting reported spend or the arm's estimate. Runs are interleaved by task, so a stopped run stays
paired.

<Aside type="caution" title="Before you publish numbers">
Publish the manifest name, task count, seed, arms file, model ids, dates and the full
`report.json`. Never publish a holdout manifest, since it leaks the oracle. Report holdout results
only for tasks filed after the model's training cutoff. Shipwright's own head-to-head results will
be published here once live runs finish; none are claimed yet.
</Aside>
