The Shipwright dashboard provides a real-time web interface for monitoring pipeline progress, agent activity, daemon status, and DORA metrics. It uses WebSocket connections for live updates.

## Prerequisites

The dashboard requires [Bun](https://bun.sh) runtime:

```bash
curl -fsSL https://bun.sh/install | bash
```

## Starting the Dashboard

```bash
# Foreground (see logs in terminal)
shipwright dashboard

# Background (runs in detached mode)
shipwright dashboard start

# Stop background dashboard
shipwright dashboard stop
```

The dashboard runs on `http://localhost:8767` by default.

## Features

### Pipeline Monitoring

View real-time progress for all active pipelines:

- Current stage and elapsed time per stage
- Self-healing cycle status
- Build agent output
- Test results and coverage
- Review findings

### Agent Activity

Track all running Claude Code agents:

- Heartbeat status (alive, stale, dead)
- Current task and iteration count
- Token usage per agent
- Session mapping (which tmux pane)

### Daemon Status

Monitor the autonomous daemon:

- Active jobs and queue depth
- Worker utilization and auto-scaling decisions
- Issue triage scores
- Recent completions and failures

### DORA Metrics

Live DORA/DX metrics dashboard:

- **Lead Time** — time from issue creation to PR merge
- **Deployment Frequency** — pipelines completed per day
- **Change Failure Rate** — percentage of pipelines that fail
- **Mean Time to Recovery** — time from failure to successful retry

### Context Efficiency

The dashboard includes a context efficiency widget that visualizes how pipeline agents use their context budgets:

- **Budget Utilization** — Gauge showing average percentage of context budget used per iteration
- **Trim Ratio** — Average percentage of generated content trimmed by the context engineering layer
- **Chars Discarded** — Total characters saved by intelligent trimming
- **Trim Events** — Number of iterations where trimming occurred

Data comes from `loop.context_efficiency` events emitted during build iterations. The `/api/context-efficiency` endpoint provides the raw metrics with a configurable time period (default: 7 days).

### Predictions

When the intelligence layer is enabled, the dashboard displays prediction data for active pipelines:

- Predicted completion time
- Success probability
- Estimated cost
- Risk factors for each stage

This data comes from the predictive analytics module. See the [Intelligence guide](/shipwright/guides/intelligence/) for configuration.

## Architecture

The dashboard consists of:

| Component      | Location                     | Purpose                                               |
| -------------- | ---------------------------- | ----------------------------------------------------- |
| **Server**     | `dashboard/server.ts`        | Bun WebSocket server, reads pipeline state and events |
| **Frontend**   | `dashboard/public/`          | HTML/CSS/JS single-page application                   |
| **Events**     | `~/.shipwright/events.jsonl` | JSONL event stream consumed by the server             |
| **State**      | `.claude/pipeline-state.md`  | Pipeline state file polled for updates                |
| **Heartbeats** | `~/.shipwright/heartbeats/`  | Agent liveness data                                   |

The server watches the events file and pipeline state for changes, pushing updates to connected clients via WebSocket.

## Configuration

The dashboard reads from standard Shipwright configuration locations. No additional configuration is required beyond having a running pipeline or daemon.

To change the port:

```bash
shipwright dashboard --port 8080
```

The dashboard listens on `127.0.0.1` (localhost only) by default. To reach it from another machine, opt in with `--host` or the `SW_DASHBOARD_HOST` environment variable:

```bash
shipwright dashboard --host 0.0.0.0                # Server or fleet mode
SW_DASHBOARD_HOST=0.0.0.0 shipwright dashboard     # Same, via environment variable
```

Binding to `0.0.0.0` exposes the dashboard on every network interface. Only do this on a network you trust, and see [Fleet](/shipwright/guides/fleet/) for how workers join a shared dashboard.

An exposed dashboard needs **GitHub OAuth** and a fleet token (`SHIPWRIGHT_FLEET_TOKEN` or `SHIPWRIGHT_FLEET_TOKEN_FILE`). It refuses to start with `auth=none`, and it refuses PAT sign-in, because PAT sign-in trusts a typed GitHub username. PAT sign-in still works on loopback. Full rules: [docs/dashboard-exposure.md](https://github.com/sethdford/shipwright/blob/main/docs/dashboard-exposure.md).

## Roles and access

Every state-changing request is checked on the server against the signed-in user's role before any handler runs. Hiding a button in the UI is only a convenience.

| Role | Can |
| --- | --- |
| `viewer` (default) | See everything |
| `operator` | Also intervene in runs (abort, pause, resume, skip, message, claim), approve or reject gates, and start, stop, pause or resume the daemon |
| `admin` | Also configure machines, notifications and gates, and manage users, join tokens and invites |

How a user gets a role, in order:

1. An entry in `~/.shipwright/rbac.json` under `users`.
2. A GitHub admin of `DASHBOARD_REPO` is an `admin`, so a fresh install is never locked out of user management.
3. Everyone else gets `default_role` from `rbac.json`, which is `viewer` when the file is missing or invalid.

An unknown role string, or a session with no role, is treated as `viewer`. A refused request returns `403` with `{"code":"role_forbidden","required":"<permission>"}` and a readable `error`, which the UI shows. Auth-off mode is single-user, is allowed only on loopback, and has no role check.
